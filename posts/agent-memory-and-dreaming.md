> 原文：https://www.anthropic.com/research/components-of-agent-memory

当 Agent 执行跨越多个会话的任务时，只保存完整聊天记录，往往还不够。历史内容越来越多，模型需要知道哪些经验值得复用、到哪里找，以及找到的内容是否仍然可信。

Anthropic 将事后回顾历史记录、整理和核查记忆的过程称为 **Dreaming**。它可以修正笔记、组织 wiki、补充链接，也可以选择哪些信息应在下一次会话开始时自动加载。

这里的“学习”发生在外部记忆中，不涉及模型权重更新。模型把经验写入文件或其他存储，后续再读取这些内容。

理解这套机制，可以从四个问题入手。

## 一、记什么：优先保存难以重新获得的信息

### 1. 记忆能带来收益，但模型需要会使用它

原文首先使用 CL-Bench 的数据库任务做对照：每道题开启新会话，一组可以通过共享目录保留记忆，另一组不保留跨题记忆。回答后，模型会获得正确答案反馈，并有机会记录经验。

| 模型 | 无记忆得分 | 有记忆得分 |
| --- | ---: | ---: |
| Opus 5.5 | 0.655 | 0.838 |
| Sonnet 5.5 | 0.644 | 0.833 |
| Opus 5 | 0.564 | 0.828 |
| Opus 4.7 | 0.383 | 0.700 |
| Sonnet 5 | 0.306 | 0.610 |
| Sonnet 4.6 | 0.330 | 0.364 |

这些数值是任务平均奖励分，不应直接解释为完整答对题目的比例。

不同模型形成了不同的记忆方式：有的保存未验证的猜测，有的纠正历史答案，较强模型则记录规则、规则的验证依据，以及已经发现的陷阱。

有效的经验积累由此形成一个循环：

**尝试 → 获得反馈 → 检查原因 → 修正认识 → 记录经验 → 用于下一次任务。**

这组实验支持：在这些任务里，允许模型积累和复用经验，通常能提高表现。但它没有单独证明某一种笔记格式就是提升的原因。

### 2. 实时状态与长期经验，保存价值不同

《宝可梦》案例展示了两种截然不同的记录习惯。

| 模型 | 约一万步时的记忆规模 | 游戏进度 |
| --- | --- | --- |
| Sonnet 3.7 | 413 个文件，977,930 个字符 | 1 枚徽章 |
| Fable 5 | 10 个文件，43,406 个字符 | 4 枚徽章 |

Sonnet 3.7 保存了大量战斗、物品和人物记录，也记录钱有多少、当前在哪等不断变化的状态。这些信息有些可以直接从画面读取，笔记却很快过期。它还反复创建“主版本”和“整合版”目录，甚至连续 17 步只整理文件，没有在游戏中行动。

Fable 5 更倾向保存当前目标、路线计划和玩法经验。这些信息需要通过探索形成，无法仅靠当前画面恢复。

一个实用的判断问题是：

> 如果不保存这条信息，下一次重新获得它，要付出多大代价？

例如，项目当前分支可以通过 Git 查询；一次隐蔽故障的触发条件、已经排除的假设和验证依据，重新获得的成本可能高得多。

当然，短期状态也可能需要保存，尤其是任务会中断、状态无法重新观测时。关键在于区分其用途，并标明时效。

### 3. 自主判断与规则引导，要分开讨论

原文发现，要求 Opus 5 和 Opus 4.7“只记录失败”，会削弱记忆收益。这样的限制可能排除了成功验证的规则和有效策略。

但对 Sonnet 4.6，明确提醒“回答前读取记忆，并验证自己的猜测”，则让得分从 0.364 提升到 0.641。

两者针对不同问题：前者限制记录内容，后者帮助模型执行必要步骤。因此，不能将结果概括成“所有规则都有害”。更合理的做法是说明记忆的用途和任务目标，再根据模型能力决定需要多少流程引导。

另外，《宝可梦》的两个模型各运行一次，只能展示不同的记录行为及其伴随结果。若要验证“精简记忆是否更好”，还需要同一个模型在不同记忆策略下进行多次对照。

## 二、怎么组织：让信息更容易找到，并适合后续任务

### 1. 从原始记录，到专题知识，再到入口索引

原文讨论了几种互相配合的记忆形式：

| 层次 | 主要作用 | 示例 |
| --- | --- | --- |
| 原始会话与操作记录 | 保存可回查的经历和证据 | 请求结果、执行日志、用户反馈 |
| 记忆笔记 | 保存值得复用的事实和经验 | 已验证规则、决策、踩坑记录 |
| wiki 等知识结构 | 整合主题，连接分散信息 | 专题页、合同页、关联链接 |
| 自动加载的顶层内容 | 提供必要背景和查找入口 | 关键约定、简短提示、索引 |

这几层可以互相链接。顶层不需要装下全部细节，模型可以沿索引按需读取，再回查原始依据。

顶层尤其需要克制：每次自动加载都会占用上下文，错误内容可能反复影响后续会话，过长的指令也可能降低遵循程度。

### 2. wiki 更适合需要关联和综合的问题

原文使用约 35 万个文件、4.2 亿 tokens 的资料建设 wiki，并用 25 个问题评估。随着建设投入增加，结果如下：

| 答题方式 | 结果 |
| --- | --- |
| 只搜索原始资料 | 得分约 53% |
| 只使用 wiki | 从早期 13% 提升到最高 48% |
| wiki 配合搜索 | 从 54% 提升到 61% |

wiki 配合搜索还平均每题节省约 2 万 tokens。这里的百分比表示评分标准的满足程度。

一种合理解释是：wiki 帮助模型理解主题、找到关联和搜索方向，原始资料搜索则补充细节并核实结论。仅靠 wiki，可能遗漏尚未整理进去的信息。

在另一个并购测试中，对于需要跨文档综合、判断或计算的相关题目，查阅 wiki 的得分为 87%，仅搜索为 73%。但当答案能从单份文档直接检索时，wiki 没有显示出明显收益。

因此，是否值得建设 wiki，取决于它能否减少后续反复查找、关联和整合信息的工作。

### 3. 组织方式要服从信息的精度要求

合同任务中的一个失败案例很有代表性：多个 Agent 同时向一张共享表格写摘要，出现条款遗漏和互相覆盖。根据这份 wiki 生成的法律分析，只包含 57 项要求中的 41 项，约 72%。

经过反思并修改建设指令，方案变成：每份合同独立成页，由单个 Agent 编写，关键条款逐字引用，并明确强调条款的重要性。改进后，全部评分标准都能满足。

这里有两个独立的工程问题：

- **表达精度**：合同条款的措辞可能影响含义，摘要不能随意代替原文。
- **写入协作**：多个 Agent 修改同一内容，需要避免覆盖，或者划分明确的写入范围。

这也说明，精简不是唯一目标。需要保留多少细节，应由任务决定。与此同时，这次实验同时调整了指令、结构和协作方式，不能把全部提升单独归因于某一个因素。

## 三、如何纠错：记忆是可修订的认识

### 1. 错误记忆会影响行动，也会影响对失败的解释

月见山案例中，Claude 将宝可梦中心的位置记错，进而认为自己已经穿过山洞。随后，它走下单向台阶，回到之前的路线。

由于导航工具没有显示落差，它将失败解释为“往西走过头了”，没有修正最初的位置判断。错误记忆因此得以保留，并继续影响行动。

Dreaming 对照原始会话记录发现并纠正位置错误后，模型重新进入山洞，最终到达下一座城市。保留错误记忆的运行则多次走回旧路线，最终未能到达目标。

这个案例支持一次具体的因果链：**修正关键记忆，改变了后续判断和路线。** 但它没有证明完整 Dreaming 流程一定优于任务内的针对性复查，也没有充分说明自动触发与等待成本。

### 2. 核查结论，也要核查证据强度

原文还举过一个抓捕经验：连续失败后，改变按键时机，随后抓捕成功，模型便把这个做法记了下来。

这样的记录可以成为后续验证的假设，但一次成功不足以确认因果关系。如果记忆直接将其表述为确定规律，后续模型就可能过度信任它。

对于重要记忆，可以考虑同时保存：

- 结论及适用条件。
- 原始依据或来源位置。
- 验证范围与尚未确认的部分。
- 与时效有关的信息。

这是一种工程建议，并非原文验证出的唯一最佳格式。其目的，是让后续使用者能够判断该相信到什么程度。

原始记录也有边界：它可以证明当时观察到什么、执行了什么，但工具观测可能不完整，记录未必足以证明真实机制。

### 3. 纠错也包括修复知识库结构

Dreaming 的作用不只体现在事实修正。原文的一次后续整理修复了 9 个指向缺失页面的链接，将其重新指向已有的对应页面，并新增 3 个页面，其中包括索引。

这类修补改善的是可访问性：知识即使已经存在，入口错误或链接断裂，也可能让模型找不到它。

## 四、何时维护：平衡即时可用性、延迟和计算成本

### 1. 即时记录和后台整理各有代价

| 方式 | 收益 | 代价 |
| --- | --- | --- |
| 执行任务时记笔记 | 重要信息马上可供后续使用 | 分散注意力，占用任务时间和计算 |
| 后台 Dreaming | 可以跨会话回顾、核查和重组 | 整理结果可能来不及帮助当前任务 |

因此，Dreaming 展示了离线纠错的价值，并不意味着连续执行的任务已经解决实时自救问题。

对于反复失败的任务，一种值得测试的设计是触发局部复查：先检查当前决策依赖的关键记忆，再决定是否需要更广泛的整理。它是否优于完整 Dreaming，需要进一步实验。

### 2. 维护可以按变化风险和使用频率安排

持续检查所有记忆通常成本过高。原文提出，可以关注容易变化的信息，并根据访问频率等因素调整 Dreaming 周期。

从工程角度，还可以考虑在出现矛盾、反复失败、任务阶段切换或重要来源更新时，触发有针对性的检查。这些是设计方向，不应当作已经验证的最佳调度策略。

后台任务的触发方式和运行位置，也取决于产品实现。“Dreaming”这个概念本身，不意味着必须等待电脑空闲，更不意味着电脑关机后仍会运行。

### 3. 评估成本，要包含整个生命周期

wiki 配合搜索每题节省 tokens，是使用阶段的收益。完整评估还需要计入：

**建设成本 + 更新核查成本 + 每次检索与答题成本。**

如果同一知识库会被反复使用，前期投入更有机会被摊薄；如果只是一次性任务，建设复杂 wiki 未必划算。

同样需要计入延迟：即使整理后得分更高，等待时间也可能不符合实时任务的要求。

## 对 Agent 系统设计的启示

这篇文章没有给出统一的最佳记忆方案，但它提供了一组清晰的设计问题：

| 设计问题 | 需要判断的内容 |
| --- | --- |
| 记什么 | 信息是否值得复用，重新获得它要付出多少代价 |
| 怎么组织 | 怎样帮助模型定位、关联和核实信息 |
| 如何纠错 | 结论是否有依据，是否过时，结构是否仍可访问 |
| 何时维护 | 当前收益是否值得付出时间、计算和更新成本 |

评估时，还要区分三种结论：某次运行观察到了改善；对照实验支持某项改进有效；系统在实际任务中具有稳定、划算的收益。它们需要的证据并不相同。

记忆系统的质量，最终体现在后续任务能否更可靠地完成。文件更少、wiki 更大、整理更频繁，都不能单独作为成功标准。
