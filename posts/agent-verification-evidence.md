让 Agent 改代码，最容易判断的是它有没有生成文件。更难判断的是，改动有没有真正解决问题，以及已有功能是否仍然可用。

阅读 Addy Osmani 发表于 claude.dev 的《How the Claude Code team thinks about verification》后，我更关心的是一件具体的事：Agent 交付时，应该拿出什么证据，才能让我们相信这次修改完成了。

这篇笔记先简述原文观点，再用开放平台的多环境转发需求展开设计。后面的用例、流程和记录格式，是结合我们项目的推演，尚未构成一份已执行的完整测试报告。

## 从测试结果走到功能结果

原文重点讨论三类验证：通过真实入口执行完整流程的端到端测试，围绕性质生成输入寻找反例的属性测试，以及对同样输入比较两套实现的差分测试。它还建议将项目的启动与验证方法写入 verify skill，并根据改动选择检查项，为具体提交保留证据。涉及评审标准时，要避免待检查的改动自行放宽判定条件。[原文](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

可以把它们对应到三个问题。

| 方式 | 要回答的问题 | 适合获得的证据 |
| --- | --- | --- |
| 端到端测试 | 用户能否通过正常入口完成任务 | 操作路径、接口响应、持久化结果、实际业务结果 |
| 属性测试 | 约定在一组输入中是否持续成立 | 不变量、输入生成范围、失败反例 |
| 差分测试 | 新旧实现的行为差异是否符合预期 | 相同输入、两侧结果、差异说明 |

三者可以在不同层次独立使用。一次修改需要哪些验证，应由变更内容、影响范围和失败后果决定。

## 用多环境转发定义完成标准

我们的开放平台原先是一条接口绑定一个服务集群，集群配置一个上游地址。改造后，集群可以配置多个环境，请求通过 x-dip-env 选择上游。

约定包括以下行为。

- 接口继续关联原 serviceId。
- 请求头名称和环境值不区分大小写。
- 未传或未匹配环境时使用 prod。
- 旧集群的原地址在新模型中作为 prod。
- 已匹配但停用的环境返回失败。
- 已选上游发生连接错误时返回失败。

以这些约定为起点，才能讨论“测试通过”意味着什么。仅确认页面出现环境标签，覆盖不到保存、加载、路由选择和真实转发等后续步骤。

## 端到端测试：从配置入口走到实际上游

一次完整验证可以使用专门的测试应用和回显服务。让不同上游返回各自的环境标识，避免两个业务环境返回相同数据时，无法判断请求去了哪里。

一个基础流程如下。

1. 从管控台打开历史服务集群，确认原地址显示为 prod。
2. 添加 test 地址并保存，记录本次操作结果。
3. 重新读取集群配置，确认地址和启用状态确实保存。
4. 等待或轮询网关配置刷新，设置明确的超时边界。
5. 通过网关正常调用接口，分别传入 prod、test 和混合大小写的环境值。
6. 同时检查上游回显和网关最终转发地址。

这里应当保留多个观察点。

| 观察点 | 能说明什么 |
| --- | --- |
| 保存接口返回成功 | 后端接受了这次保存请求 |
| 重新查询配置一致 | 配置已持久化并能读回 |
| 网关日志选择 test | 运行中的网关识别了环境 |
| test 上游收到请求 | 请求实际到达了选定目标 |
| 返回的业务结果符合预期 | 用户可获得正确结果 |

假设配置已经保存，但请求仍然到旧地址，这些证据可以帮助继续区分配置刷新、接口绑定、环境选择和路径重写等问题。

### 短暂成功提示应该怎样验证

保存提示可能只显示几秒，等截图时已经消失。自动化可以在点击保存前注册响应或提示等待，然后执行操作，减少错过瞬态事件的机会。

但真正需要验证的目标，还包括重新查询配置、刷新页面后的结果，以及实际调用行为。成功提示适合辅助说明过程，持久化与业务结果则负责确认操作的实际效果。

## 属性测试：先写出必须成立的规则

属性测试需要先定义性质，再生成多种输入尝试推翻它。这里可以直接作用于环境解析函数，也可以作用于服务层或 API。

### 大小写归一化

对于一个已配置且启用的环境标识，在合法字符范围内改变大小写，选择结果应保持一致。

```text
resolve(config, "test")
resolve(config, "TEST")
resolve(config, "TeSt")
```

三次结果都应指向 test。测试头名称是否大小写无关，还需要使用真实 HTTP 请求头容器或请求链路验证。

### 未知环境的默认行为

先生成合法且包含 prod 的配置，再生成一个与所有环境标识均不匹配的值，验证最终选择 prod。

输入范围需要写清楚。一个已配置但停用的 test，属于匹配到不可用环境，预期应为失败。将它归入“未知环境”会测试错规则。

### 配置规范化的幂等性

若配置保存前会去除首尾空格、统一大小写，同一配置连续规范化两次，结果应相同。

```text
normalize(normalize(config)) == normalize(config)
```

幂等性的比较对象是规范化结果。保存时重建的记录 ID、更新时间等字段，需要根据各自契约单独判断。

### 路径和查询参数的保留

为包含基础路径的上游地址生成输入，检查最终请求路径是否只拼接一次。查询参数中的编码字符、重复键和空值，也需要保留约定的语义。

例如，上游地址包含 /base，接口路径是 /whoami，最终应得到 /base/whoami。测试输入还应覆盖带尾斜杠和多段路径的情况。

输入生成只负责扩大探索范围，正确的性质仍然需要人和 Agent 根据业务契约共同定义。

## 差分测试：明确哪些行为需要保持

多环境改造包含大量存量数据，适合将旧版网关作为比较对象。

首先固定一组历史单地址配置，对新旧版本发送相同请求，比较默认目标、路径重写、查询参数以及失败行为。对时间戳、链路 ID 等字段，只有在确认其与测试目标无关后，才做归一化。

新增能力则需要明确预期差异。

| 场景 | 比较目标 |
| --- | --- |
| 旧集群不传环境头 | 新旧默认转发行为一致 |
| 旧集群传未知环境 | 保持约定的兼容行为 |
| 多环境集群传 test | 新版本转发到 test，依据新契约验证 |
| 多环境集群选中停用项 | 按新契约返回失败 |

旧系统也可能有缺陷，因此发现差异之后，仍需判断是回归、预期变更，还是对历史问题的修复。允许变化的范围应提前说明，并关联需求。

## verify skill：把项目的验证入口写清楚

可以为开放平台整理一份项目自己的 verify skill，让 Agent 找到可执行的方法。

| 内容 | 在项目中需要写清楚的事项 |
| --- | --- |
| 启动 | 前后端、网关的命令、端口和就绪判断 |
| 环境 | 当前版本、Apollo 环境、数据库和外部依赖 |
| 身份 | 测试账号、登录方式和所需权限 |
| 数据 | 专用测试应用、集群、回显服务及清理方式 |
| 检查 | 修改影响哪些流程，每项预期结果是什么 |
| 失败处理 | 记录失败步骤、响应、日志和必要截图 |
| 交付 | 代码版本、实际执行项、结果和未验证范围 |

我们最近的联调就说明了环境说明的重要性：页面运行在本地，可以连接本地演示数据，也可以通过本地后端连接 test 数据库。同一个页面地址，并不能完整说明验证了哪套系统。

因此，启动成功后还应确认运行配置。前端页面能打开、后端端口可访问、业务返回成功，分别是不同的检查点。

## 验证本身也需要维护

一个容易失去价值的测试是偶发失败后只靠重跑通过。处理时应保存失败证据，查明等待条件、测试数据冲突、依赖故障或真实并发问题。

验证规则也需要审查。若同一个提交既修改业务，又放宽阻断它的检查标准，结果可能失去约束。规则变更可以作为显式改动接受评审，验证结果则应绑定被检查的提交。

对于我们自己的流程，可以保留简短的交付记录。

```text
变更版本：提交 SHA
验证环境：前端、后端、网关版本及数据源
执行范围：本次实际执行的检查
结果依据：请求响应、配置回读、上游回显或日志
失败与限制：尚未通过或尚未覆盖的项目
```

已经部署的历史版本，不能自动继承本地新版本的测试结论。发布后仍要确认产物来源、实例就绪和实际访问结果之间的对应关系。

## 将测试投入放在本次变更上

如果只调整环境标签的颜色和展开布局，应该重点检查渲染、交互、长地址、复制以及窄屏显示。若修改环境解析、数据迁移或缓存分区，则需要增加相应的属性、兼容性和真实转发验证。

不必每次运行所有测试，但每次都应说明选择依据，并检查现有测试能否覆盖当前风险。

对我来说，这次调研最直接的收获，是在交给 Agent 编码之前，就把用户入口、预期行为、失败条件和可获得的证据写清楚。这样，交付评审才能围绕具体结果展开，也更容易发现仍未完成的步骤。
